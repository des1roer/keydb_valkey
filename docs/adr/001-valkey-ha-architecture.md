## Контекст

Проект предполагает горизонтальное масштабирование Valkey-бэкенда для PHP-приложения, которое хранит данные в Redis-совместимом key-value хранилище. На момент принятия решения три сервиса работали одновременно (KeyDB, Valkey, Redis) с отдельными конфигурациями HA.

Требуется выбрать архитектуру, которая обеспечивает:
- высокую доступность при отказе ноды;
- максимальный throughput при минимальной латентности;
- горизонтальное масштабирование без остановки сервиса;
- возможность бесшовной миграции данных из KeyDB.

## Решение

Использовать нативный Valkey Cluster (3 primary + 3 replica) как основную архитектуру HA вместо мастер-реплики с внешним load balancer (HAProxy).

## Обоснование

Бенчмарки (100K SET-запросов, 50 concurrent клиентов, 256B payload) показали:

| Сценарий                                            | Throughput (req/s) | Avg latency (ms) |  p50 (ms) |  p95 (ms) |  p99 (ms) |
|-----------------------------------------------------|-------------------:|-----------------:|----------:|----------:|----------:|
| Valkey master-replica, прямое подключение к мастеру |             41 118 |            0,832 |     0,719 |     1,335 |     1,911 |
| **Valkey Cluster (3+3)**                            |         **99 800** |        **0,422** | **0,407** | **0,631** | **0,799** |
| Redis master-replica через HAProxy                  |              5 534 |            8,265 |     1,583 |    75,455 |    77,887 |

> **Факт:** Valkey Cluster показал ~2.4x больше throughput и ~2.4x меньшую медианную латентность по сравнению с одиночным мастером.

> **Факт:** HAProxy в цепочке master-replica вносит значительный оверхед: p99 latency достигал 77,887 мс против 1,911 мс при прямом подключении. Точная причина (конфигурация HAProxy, сетевой оверхед, характеристики Redis-сервера) требует отдельного исследования.

Кластер распределяет hash slots между тремя primary-нодами, что позволяет утилизировать ресурсы трёх серверов параллельно. Реплики обеспечивают автоматический failover без участия внешней системы (Sentinel или HAProxy). Рассмотрены 4 варианта (подробнее ниже).

**Тестирование failover (Sentinel, docker-compose-valkey.yaml).** Выполнен на лабораторной конфигурации: один primary, один replica, один Sentinel. Сценарий: `docker stop valkey_primary`, ожидание 15 секунд, проверка состояния.

До failover:
- `valkey_primary` — `role:master`, `connected_slaves:1`;
- `valkey_replica` — `role:slave`, `master_host:valkey_primary`;
- Sentinel: `get-master-addr-by-name` → `172.21.0.2:6379`;

После failover (15 секунд):
- `valkey_replica` — `role:master`, `connected_slaves:0`;
- Sentinel: `get-master-addr-by-name` → `172.21.0.3:6379` (IP реплики);

> **Результат:** Sentinel корректно промотил replica на master за 15 секунд. Кворум был достигнут (quorum: 1 из 1). Время failover соответствует `down-after-milliseconds` (5 000 мс) + время выполнения промоушена.

> **Замечание:** для production рекомендуется 3 Sentinel-ноды для защиты от потери кворума при отказе одной Sentinel-ноды.

## Последствия

Плюсы:

* Throughput ~2.4x выше одиночного мастера (99 800 против 41 118 req/s);
* Латентность ниже (p99: 0,799 мс против 1,911 мс);
* Автоматический failover — при потере primary её replica поднимается за ~5-10 с (cluster-node-timeout);
* Нет единой точки отказа (HAProxy, Sentinel);
* Горизонтальное масштабирование — можно добавить ноды и перераспределить слоты;
* Проще операционная модель: 6 нод вместо 6-7 (нет Sentinel + HAProxy);
* phpredis RedisCluster автоматически обрабатывает MOVED/ASK редиректы;
* Миграция из KeyDB осуществляется RedisShake (sync_reader → redis_writer cluster).

Минусы:

* Кластер не поддерживает мульти-ключевые операции (MGET, MSET, транзакции), если ключи попадают в разные слоты;
* Приложение обязано использовать RedisCluster клиент;
* Hash tags (`{user:1000}`) необходимы для мульти-ключевых операций внутри одного слота;
* Cluster bus потребляет дополнительные порты (+10000 к каждому клиентскому порту);
* Сложнее отладка: ключи распределены по нодам, операции требуют cluster-aware CLI.

Технический долг:

* Необходимо оценить, насколько приложение использует мульти-ключевые операции;
* p99 latency при подключении через HAProxy требует отдельного расследования — возможно, оптимизация конфигурации HAProxy даст приемлемые результаты для master-replica режима.

## Вариант А: Valkey master-replica + Sentinel

Один primary, один replica, 3 sentinel-ноды для автоматического failover. Приложение подключается напрямую к мастеру.

Плюсы:

* Прямое подключение к мастеру даёт хороший throughput (41K req/s, p99 1,9 мс);
* Простота концепции — знакомая модель;
* Все ключевые операции (MGET, MSET, транзакции) работают без ограничений;
* Write-нагрузка на одну ноду не создаёт конфликтов.

Минусы:

* Write ограничено одной нодой;
* Sentinel занимает 3 дополнительных контейнера;
* Failover через Sentinel (~10-30 с) медленнее кластерного;
* Нет горизонтального sharding-а;
* Роль replica пассивна — CPU/RAM реплики простаивают при reads (если не читать с реплики).

Рекомендация: Подходит для небольших нагрузок (<50K req/s) или если write-throughput упирается в одну ноду.

## Вариант Б: Valkey master-replica + HAProxy

Один primary, один replica, Sentinel, HAProxy для прозрачной маршрутизации и failover.

Плюсы:

* Прозрачная маршрутизация для приложения — не нужно знать адрес мастера;
* HAProxy можно настроить на балансировку чтения по реплике.

Минусы:

* HAProxy добавляет latency (p99: 77,887 мс в бенчмарке) — **факт**, причина требует исследования;
* Единая точка отказа (HAProxy);
* Write только на master;
* Больше сервисов для поддержки: Sentinel + HAProxy = 5 контейнеров;
* write-throughput ~5,5K req/s через HAProxy.

Рекомендация: Не рекомендуется для production при текущей конфигурации. Возможно рассмотреть после оптимизации HAProxy.

## Вариант В: Valkey Cluster (3 primary + 3 replica) ← Выбран

Нативная кластеризация с автоматическим sharding-ом и failover-ом. 16 384 hash slot распределены между тремя primary-нодами.

Плюсы:

* Наивысший throughput (99 800 req/s) — **факт**, подтверждён бенчмарком;
* Минимальная латентность (p99: 0,799 мс) — **факт**;
* Автоматический failover без внешней системы (cluster-node-timeout ~5-10 с);
* Горизонтальное масштабирование — можно добавить ноды и перераспределить слоты;
* Нет единой точки отказа;
* Проще операционная модель: 6 нод вместо 6-7 (нет Sentinel + HAProxy);
* phpredis RedisCluster автоматически обрабатывает MOVED/ASK редиректы;
* Миграция из KeyDB осуществляется RedisShake (sync_reader → redis_writer cluster).

Минусы:

* Мульти-ключевые операции (MGET, MSET, транзакции) ограничены одним slot — ключи должны быть в одном slot;
* Нужно использовать RedisCluster клиент;
* Hash tags (`{user:1000}`) необходимы для мульти-ключевых операций внутри одного слота;
* Cluster bus потребляет дополнительные порты (+10000 к каждому клиентскому порту);
* Сложнее отладка: ключи распределены по нодам, отладочные операции требуют cluster-aware CLI.

Рекомендация: Рекомендуется. Наилучшие показатели производительности, горизонтальное масштабирование, отсутствие единой точки отказа.

## Вариант Г: KeyDB Multi-Master (active-active)

Два KeyDB ноода, реплицирующих друг к другу через active-replica + multi-master.

Плюсы:

* Write на обе ноды;
* Нет единой точки отказа на уровне серверов;
* Минимальное количество сервисов (2+1=3 с HAProxy).

Минусы:

* Нет нативного sharding-а;
* **Предположение:** конфликтные записи при одновременной записи разных ключей на разные ноды могут привести к расхождению данных;
* Нет экосистемы миграционных инструментов (RedisShake поддерживает Redis/Valkey, не KeyDB-специфичные фичи);
* KeyDB не поддерживает cluster-режим;
* Сложная отладка при расхождении данных.

Рекомендация: Не рекомендуется для production. Подходит как источник данных для миграции.
